2. EXECUTIVE SUMMARY
================================================================================

2.1 What the project is

BilouNook (internally also called "notchdynamique") is a macOS menu-bar /
notch utility written in Swift with SwiftUI and AppKit. It draws a borderless
floating panel attached to the hardware notch area of a MacBook display,
expands it on hover or click, and shows modules inside the expanded shape.
The flagship module is a Now Playing / media controller with artwork,
transport controls, a seek bar, and a compact "live activity" strip shown
while the notch is closed. Additional placeholder modules (Module A and
Module B) exist to exercise the module system.

The app is an agent-style application: Info.plist sets LSUIElement = true, so
there is no Dock icon and no normal main window. The panel is a non-activating
NSPanel placed above the menu bar.

2.4 Health in one paragraph

The architecture is coherent and, in places, carefully engineered: dependency
injection for time and scheduling in NotchState, a provider abstraction for
Now Playing, injectable clocks in media playback, a module registry with a
protocol, a dedicated geometry layer, and a meaningful test suite. However,
the recovered tree does not build. The current build fails in
ModuleShellView.swift at line 77 with a Swift type-check timeout, and a second,
independent compile error exists because NotchRootView writes
"notchState.openOnHover" while NotchState has no such property. The Xcode
project also contains a duplicated object UUID that aliases Assets.xcassets
and MotionBench.swift, and the referenced Assets.xcassets directory is absent
from the recovered tree. Several design documents describe behaviour that the
final code no longer implements (peek phase, hover-intent delays, haptic rate
limits, panel size, spring constants), so the documentation is partly stale.
The media layout appears to render two time rows and to compute a content
height that does not include the second row, and the module tab bar is placed
into zero-width flanks using a centring calculation that overlaps the notch.
These are the highest-value items to address first.

       MediaProgressBar already renders a time row; the second row is not
       included in MediaLayout's content-height budget. [VERIFIED]
  H-4  ModuleShellView positions tab groups relative to zero-width flanks
       (the 6-point forbidden-zone expansion cancels the flank), so a two-tab
       group's nearest tab is centred about 14 points inside the notch and a
       one-tab group straddles the notch edge. [VERIFIED by arithmetic]
  H-5  Assets.xcassets is referenced by the Resources phase and by

  M-3  NowPlayingService pending-seek reconciliation can leave a seek pending

  M-4  AppleScriptNowPlayingProvider parses a "|" separated string, so titles,
       artists, or albums containing "|" corrupt the snapshot. [VERIFIED]
  L-1  Documentation drift across STATE_MACHINE.md, TESTS.md,

3.2 Purpose

The app augments the MacBook notch. It creates a transparent, borderless,
non-activating panel aligned with the notch and the top of the screen. When
the pointer enters a hot zone around the notch, or when the user clicks it,
the panel expands into a rounded notch-shaped surface and displays the active
module. When the pointer leaves, or after a watchdog interval, it collapses.
When media is playing and the notch is closed, a compact live activity strip
can extend the notch horizontally to show artwork and equalizer motion.

3.3 Platform behaviour

  - The panel is placed at the top centre of a target screen and is flush with
    the top edge. [VERIFIED in NotchAttachment]
  - The panel floats above the menu bar: NSWindow.Level.mainMenu + 3.
    [VERIFIED in NotchPanel]
  - It joins all Spaces, remains during full-screen auxiliary display, is
    stationary, and is excluded from window cycling. [VERIFIED]
  - It does not become key or main, does not activate the app, and does not
    hide on deactivate. [VERIFIED]
  - Mouse events pass through the panel except inside the current interactive
    region. [VERIFIED]

3.4 Architecture in one line

An AppKit NSPanel hosts a SwiftUI NotchRootView; NotchState is the state
machine; Interaction (MouseMonitor, Watchdog, GestureMonitor) feeds intent;
NotchGeometry and NotchShape compute the visual footprint; ModuleRegistry
selects a module; MediaModule and NowPlayingService provide media content;
SettingsStore persists user preferences; debug-only tools (AnimationLab,
MotionBench, DebugOverlay, hotkeys, diagnostics) support tuning.

3.6 What is unusual or notable

  - The app target compiles DEBUG-only files (AnimationLab, MotionBench,
    HotKeyManager, DebugOverlay, NotchAttachDiagnostics) into the normal
    target and relies on #if DEBUG. The test target compiles app sources
    directly as logic tests rather than linking against the app.
  - The panel is created and shown manually from an AppDelegate inside a
    custom @main entry point. There is no SwiftUI Scene or WindowGroup;
    SettingsWindow is a separate AppKit window. The AppKit lifecycle owns the
    panel and the settings window.
  - The Now Playing stack ships a Perl-based adapter and a private-framework
    shim, which is a pragmatic workaround for the lack of a public
    now-playing API. It is the most externally fragile part of the project.
  - A large amount of documentation and verification history is checked in
    (docs/, root *.txt). Some of it predates the final code and now
    contradicts it.

8.1 Entry point

  File: BilouNook/BilouNook/App/BilouNookApp.swift (104 lines)
  The executable entry point is a SwiftUI @main struct whose main() is written
  manually:

              let app = NSApplication.shared
              let delegate = AppDelegate()
              app.delegate = delegate
              app.run()

      }

  [VERIFIED]

  Consequences:
  - SwiftUI's normal App/Scene lifecycle is bypassed for the panel. The app
    creates NSApplication directly and runs it.
  - The @main struct is a custom entry point, not a SwiftUI App conformance;
    no WindowGroup or Settings scene is declared in this file.
  - Because there is no Scene, the Settings window is opened imperatively by
    SettingsWindow.shared, not through the standard Settings scene.
  - LSUIElement = true in Info.plist makes this an agent app.

8.2 AppDelegate launch sequence

  applicationDidFinishLaunching performs, in order [VERIFIED]:

    1. panelController = NotchPanelController()
    2. panelController?.show()
    3. DEBUG-only branches:
         a. runAttachDiagnosticIfNeeded()
              --motion-bench:
                  require panel, else exit(5)
                  Watchdog.shared.stop()
                  after 0.6 s: MotionBench.run()
                  return true
              --notch-attach-diag:
                  require panel, else exit(5)
                  Watchdog.shared.stop()
                  after 0.5 s: print closed snapshot, NotchState.shared.open()
                  after 1.5 s more: print open snapshot, exit(0)
                  return true
         b. runNotchSelfCheckIfNeeded()
              --notch-selfcheck:
                  require panel, else exit(5)
                  Watchdog.shared.stop()

9. ARCHITECTURAL OVERVIEW
================================================================================

9.1 Layering

  Layer 0 - Platform shell
    NSApplication, AppDelegate, NSPanel, NSHostingView, NSScreen, NSEvent.

  Layer 1 - State and policy
    NotchState (phase machine, timers, haptic triggers),
    SettingsStore (persistence), ScreenResolver (target display),
    ModuleRegistry (active module selection).

  Layer 2 - Geometry and visual footprint
    NotchGeometry (screen/notch metrics, forbidden zone, open/closed metrics),
    NotchShape (rounded notch path), LiveActivityLayout (wings and widths),
    NotchAttachment (panel frame aligned to screen).

  Layer 3 - Interaction
    MouseMonitor (global/local mouse events, hot zone, fly-by guard),
    Watchdog (polling safety net), GestureMonitor (scroll gestures),
    InteractionRegion (hit rectangles per phase), HapticsService (feedback).

  Layer 4 - Presentation
    NotchRootView (root layout, phase-driven content),
    ModuleShellView (module tab bar and content frame),
    MediaView / MediaContentView / MediaProgressBar / Artwork views,
    MediaCompactLiveActivity, DebugOverlay, SettingsContentView.

  Layer 5 - Services
    NowPlayingService (orchestration, seek reconciliation),
    NowPlayingProvider implementations (MediaRemote, AppleScript),
    ArtworkDecoder / ArtworkThumbnailCache / ArtworkAverageColor,
    SourceAppInfoCache.

  Layer 6 - Development tooling
    AnimationLab, MotionBench, DebugOverlay, HotKeyManager,
    NotchAttachDiagnostics, calibration state, debug logging.

9.2 Design patterns present

  State machine
    NotchState is an explicit phase machine with closed, peek, open, opening,
    closing. It has injectable clock and scheduler protocols, generation
    counters to invalidate stale scheduled work, and dwell-time guards.

  Protocol abstraction
    NotchModule defines the module contract.
    NowPlayingProvider defines the media-source contract.
    NotchClock, NotchScheduler, and NotchScheduled isolate time and scheduling.

  Registry / plugin
    ModuleRegistry owns an ordered array of modules and exposes the active
    module and active live activity. Modules can be enabled or disabled.

  Observer / callback
    MouseMonitor exposes closures; NowPlayingService exposes @Observable
    state; SettingsStore is an ObservableObject with @Published properties.

  Coordinator / controller
    NotchPanelController owns the panel and hosting view and handles
    repositioning. AppDelegate owns the controller.

  Value types for geometry
    NotchMetrics, NotchGeometry, LiveActivityLayout, MediaLayoutMetrics, and
    MediaShapeGeometry are value-oriented, which makes them testable.

9.3 Strengths

  - Geometry is isolated from views and is covered by tests
    (NotchGeometryTests, NotchPanelTests, NotchAttachmentTests,
    CompactLayoutTests, LiveActivityLayoutTests).
  - NotchState is testable without real time because of the clock/scheduler
    injection. NotchStateTests uses a fake clock and scheduler.
  - NowPlayingService accepts injected providers, which
    NowPlayingServiceTests exploits.
  - Media playback projection uses an anchor (MediaPlaybackAnchor) instead of
    mutating elapsed time on every frame, which is the right approach for
    smooth progress.
  - The module protocol is small and the registry is straightforward.
  - The app degrades to AppleScript if MediaRemote is unavailable.

9.4 Weaknesses

  - The state machine and the view disagree about the existence of
    openOnHover and about whether peek is reachable.
  - The root view owns too much: lifecycle, monitors, geometry updates,
    settings propagation, animation orchestration, and debug hooks. It is a
    303-line view with 14 onChange handlers.
  - Settings are copied into NotchState once on appear and then kept in sync
    with onChange. This is workable but fragile; a single missing onChange
    silently desynchronises behaviour.
  - The panel's size is a fixed 568 x 220 while the visual shape is
    phase-dependent. The panel is a canvas, not the shape, which is correct,
    but it means hit testing and layout must be kept in sync manually.
  - Documentation is treated as a design log rather than a maintained
    specification, so it drifts.
  - The DEBUG-only utilities are compiled into the app target and guarded by
    #if DEBUG. This is common for a solo project but increases the surface of
    the production target's source graph.

9.5 Control flow summary

  Mouse enters hot zone
    -> MouseMonitor.onEnterHotZone
    -> NotchState.enterIntent
    -> after intentDelay (default 0) requestOpen(.hover)
    -> phase .opening then .open
    -> NotchRootView.onChange(.open)
    -> animate metrics to activeOpenMetrics
    -> after 0.05 s showContent = true
    -> panel.ignoresMouseEvents updated by updateMouseInteraction

  Mouse leaves open area
    -> MouseMonitor.onLeaveOpenArea
    -> NotchState.requestClose(.mouseLeft)
    -> phase .closing
    -> after closeDelay (default 0) phase .closed
    -> NotchRootView.onChange(.closed)
    -> hide content, animate metrics to closedMetrics
    -> after 0.2 s panel.ignoresMouseEvents = true

  Watchdog
    -> every 0.25 s reads mouse location
    -> if outside interactive rect, calls watchdogTick(isOutside: true)
    -> after 0.5 s outside, closeImmediately(.watchdog)

  Media update
    -> provider emits NowPlayingSnapshot
    -> NowPlayingService.accept
    -> pending seek reconciliation
    -> snapshot published
    -> MediaViewState maps to .empty or .track(MediaPresentation)
    -> MediaContentView renders
    -> MediaModule.liveActivity reflects isPlaying
    -> ModuleRegistry.activeLiveActivity changes
    -> NotchRootView recomputes closed metrics (wings)

10. MODULE-BY-MODULE ANALYSIS
================================================================================

10.1 App and windowing

  BilouNookApp.swift
    Manual NSApplication entry point and AppDelegate. Owns the panel
    controller and the Now Playing service lifecycle. Contains four DEBUG
    command-line modes (motion bench, attach diagnostic, notch self-check,
    smoke test) plus a calibration visibility flag. 104 lines.

  NotchPanel.swift
    NSPanel subclass and controller. The panel is borderless,
    non-activating, transparent, shadowless, non-movable, and floats above the
    menu bar. The controller attaches a NotchRootView, shows the panel, and
    repositions it on screen and wake changes. 81 lines.

  NotchAttachment.swift
    Pure geometry helper: hardware notch rect, backing-aligned rect, and panel
    frame (centred horizontally, flush to the top of the screen). 44 lines.

  NotchAttachDiagnostics.swift
    DEBUG-only diagnostic printer and self-check. Reports screen frame,
    visible frame, backing scale, safe-area insets, auxiliary top areas,
    hardware notch rect, panel frame, panel level, menu-bar owner and layer,
    and whether the panel is above the menu bar. 167 lines.

10.2 Notch presentation

  NotchRootView.swift
    The root SwiftUI view. It owns NotchState, ModuleRegistry, SettingsStore,
    panel reference, current metrics, content visibility, and last open
    trigger. It renders a ZStack containing the notch shape, the module shell,
    compact/live activity content, and debug overlay; applies scale/blur
    transitions; wires monitors and hotkeys; and reacts to phase, module,
    live-activity, and settings changes. 303 lines.

  NotchGeometry.swift
    Computes NotchGeometry for a screen and settings: screen frame, backing
    scale, hardware notch rect, safe-area top, width/height deltas, flare and
    bottom radius overrides. Provides closedMetrics, openMetrics, forbidden
    zone, top-band flanks, and overlap/virtual-notch constants. 264 lines.

  NotchShape.swift
    Animatable Shape that draws the notch silhouette with independent
    top-left, top-right, bottom-left, bottom-right radii and quadratic curves.
    Metrics are clamped through NotchShapeMetrics. 94 lines.

  LiveActivityLayout.swift
    Computes compact live-activity width and wings. Uses the hardware notch
    width when available and falls back to the closed width. 47 lines.

  DebugOverlay.swift
    DEBUG-only overlay showing screen and notch metrics, fine-tune steppers,
    and now-playing content. 311 lines.

10.3 State

  NotchState.swift
    @Observable state machine. Phases: closed, peek, open, opening, closing.
    Open triggers: hover, click, gesture, programmatic. Close reasons:
    mouseLeft, gesture, click, programmatic, watchdog, system. Injectable
    clock and scheduler. Generation counters invalidate stale scheduled
    closures. Dwell-time guards. Watchdog tick closes after 0.5 s outside.
    211 lines.

10.4 Interaction and feedback

  MouseMonitor.swift
    Singleton with global and local mouse-moved monitors. Tracks hot-zone
    entry/exit and checks the open area on every move (the leave callback can
    fire repeatedly while outside). Supports a fly-by guard using
    SettingsStore.flyByGuardEnabled and flyBySpeedThreshold. 74 lines.

  Watchdog.swift
    Singleton repeating Timer at 0.25 s. Reads NSEvent.mouseLocation,
    resolves the target screen, computes the interactive rect, and calls
    NotchState.watchdogTick. 23 lines.

  GestureMonitor.swift
    Global and local scroll-wheel monitors. Emits a PassthroughSubject of
    NotchGestureEvent (deltaY, deltaX, phase) and accumulates horizontal
    deltas to trigger onHorizontalSwipe(+/-1). Gated by
    verticalGesturesEnabled and by containment in the interactive or hot
    rect. 71 lines.

  InteractionRegion.swift
    Computes the hot zone (closed notch plus horizontal padding and top
    extension) and the interactive rectangle per phase. 77 lines.

  HapticsService.swift
    Singleton haptic player with kinds open and close. Uses
    NSHapticFeedbackManager. Cooldowns: 0.25 s for the same kind, 0.12 s for
    the opposite kind. Honours hapticsEnabled and a named pattern. Logs via
    OSLog subsystem com.bilou.BilouNook, category haptics. 71 lines.

10.5 Modules

  NotchModule.swift
    Protocol: id, title, icon, compactView, expandedView, preferredSize,
    isEnabled, liveActivityPriority, isLiveActivityActive, liveActivity.
    Defaults: compactView nil, isEnabled true, priority 0, active false,
    liveActivity nil. 22 lines.

  ModuleRegistry.swift
    @Observable singleton holding [MediaModule(), ModuleA(), ModuleB()].
    activeModuleID, activeModule (fallback first enabled), enabledModules,
    activeLiveActivity (highest priority active), select, selectNext,
    selectPrevious, transitionDirection. 74 lines.

  ModuleShellView.swift
    Renders the active module's expanded view inside the notch shape and a
    flank tab bar split into left and right halves. Wires horizontal swipes to
    module switching. 176 lines. Currently fails to type-check at line 77.

  PlaceholderModuleView.swift
    Simple placeholder content used by Module A and Module B. 22 lines.

  ModuleA.swift / ModuleB.swift
    Placeholder modules with ids module-a and module-b, SF Symbols a.circle
    and b.circle, and preferred sizes 440x140 and 520x160. 26 lines each.

  MediaModule.swift
    Module id media, icon music.note, preferred size from MediaLayout,
    liveActivityPriority 10, live activity active when mediaCompactEnabled and
    NowPlayingService.liveActivityState.isPlaying. 22 lines.

10.6 Media

  MediaView.swift
    Entry view for the media module. Defines four EnvironmentKeys
    (nowPlayingService, mediaSafeAreaOverride, mediaSourceAppOverride,
    mediaTintOverride), maps the service snapshot through MediaViewState, and
    renders either the empty state or MediaContentView. 183 lines.

  MediaViewState.swift
    Converts NowPlayingSnapshot into .empty or .track(MediaPresentation) and

  MediaLayout.swift
    The layout contract: width, clearances, artwork size, radii, column

  MediaContentView.swift
    The expanded media UI: artwork on the left; title, artist/album, progress

  MediaProgressBar.swift

  MediaPlaybackAnchor.swift
    Value type holding elapsedAtAnchor, anchorDate, and isPlaying; projects

  MediaTransport.swift
    Transport actions: toggle play/pause, next, previous (or restart when

  MediaFormatting.swift

  MediaMotion.swift
    Spring constants for media UI and reduce-motion handling. 14 lines.

  MarqueeText.swift
    Text that scrolls when it overflows, with edge fade and reduce-motion

  EqualizerView.swift

    ImageIO-based thumbnail decoding, an NSCache keyed by identity and max

13.4 Cycles and coupling risks

  Cycle 1: NotchPanel -> hosting view -> NotchRootView -> NotchPanel.
    Benign for app lifetime; problematic for tests or future multi-window.

  Cycle 2: NotchRootView -> NotchState -> HapticsService -> SettingsStore
    (read) and NotchRootView -> SettingsStore. Not a retain cycle, but a
    behavioural coupling: changing a setting can trigger haptics, which reads
    another setting, inside the same update.

  Cycle 3: ModuleRegistry -> MediaModule -> NowPlayingService ->
    NowPlayingLiveActivityState -> ModuleRegistry.activeLiveActivity. The
    registry reads module state that depends on the service, and the service
    is observed by the view that reads the registry. This is a one-directional
    observation chain in practice, but it is easy to create update loops if a
    module writes back to the service during body evaluation.

  Cycle 4: SettingsStore -> NotchRootView.onChange -> NotchState -> haptics
    -> SettingsStore. Same as cycle 2.

13.5 Layering violations

  - NotchRootView imports and drives DebugOverlay, HotKeyManager, and
    AnimationLabWindow directly, so the production view knows about DEBUG
    tooling.
  - NotchPanel.panelSize() calls MediaLayout, ModuleA, and ModuleB directly.
    The window layer depends on the module layer, which is the reverse of the
    intended direction.
  - ModuleShellView reads NotchGeometry directly and computes tab placement
    from raw flank rects, duplicating layout logic that would be better in

14. DATA FLOW AND STATE MANAGEMENT

14.1 Notch phase machine

  States:
    closed   - notch is at closed metrics; content hidden; panel ignores mouse
               except in the hot zone.
    peek     - declared and handled in the view, but never entered by the
               current state machine.
    open     - expanded metrics; content visible after a 0.05 s delay.
    opening  - transient; set and immediately overwritten by open.
    closing  - set by requestClose; transitions to closed after closeDelay.

  Transitions implemented:

    closed -> open
      requestOpen(.hover/.click/.gesture/.programmatic)
      Preconditions: not already open/opening; if closing, dwell must have
      elapsed. Cancels pending work, increments generation, plays open haptic,
      sets .opening, then .open synchronously.

    open -> closing
      requestClose(.mouseLeft/.gesture/.click/.programmatic/.watchdog/.system)
      Preconditions: not closed/closing; dwell since lastOpenTime must have
      elapsed. Cancels pending work, increments generation, plays close
      haptic, sets .closing, schedules transition to .closed after closeDelay.

    closing -> closed
      Scheduled closure after closeDelay, guarded by generation and phase.

    closing -> open
      requestOpen or enterIntent, if minStateDwell since lastCloseTime has
      elapsed. Cancels the pending close.

    closed -> closed
      requestClose is rejected.

    open -> open
      requestOpen is rejected ("already_open").

    peek
      Not produced by any transition. NotchRootView has a branch for it, and
      NotchGeometry has peekMetrics(), but neither is reachable from current
      code. [VERIFIED by grep for ".peek" and by reading requestOpen]

  Defaults:
    intentDelay = 0.0
    closeDelay = 0.0
    minStateDwell = 0.0

  With defaults, a hover open is immediate, a close is one main-queue turn
  later, and re-entry is never blocked by dwell. The 0.5 s watchdog close is
  the only built-in delay.

  Generation counter:
    Every accepted request increments generation. Scheduled closures capture
    the generation and no-op if it changed. This prevents a stale close from
    closing a newly reopened notch.

  outsideSince:
    watchdogTick sets outsideSince on the first outside tick, then closes when
    at least 0.5 s has elapsed. requestClose clears outsideSince. Because the
    watchdog runs at 0.25 s, the effective close is between 0.5 and 0.75 s
    after the pointer leaves, assuming the panel is open.

14.2 Interaction event flow

  Global mouse move
    -> MouseMonitor global monitor
    -> if inside hot zone and not previously inside: onEnterHotZone
    -> if outside open area: onLeaveOpenArea (called on every move outside,
       not only on the inside-to-outside transition)
    -> onMouseMove(point)

  Hot zone entry
    -> NotchRootView sets lastOpenTrigger = .hover
    -> NotchState.enterIntent()
    -> if intentDelay <= 0: requestOpen(.hover) immediately
    -> else schedule open after intentDelay (cancellable)

  Open area exit
    -> if phase == .open: cancelIntent(); requestClose(.mouseLeft)
    -> if phase == .closed or .peek: cancelIntent()

  Click
    -> NotchState.toggle() from .onTapGesture on NotchShape in NotchRootView;
       the panel receives clicks only where it accepts mouse events
    -> if open/opening: closeImmediately(.click)
    -> else requestOpen(.click)

  Scroll gesture
    -> GestureMonitor emits events while the pointer is in the interactive or
       hot rect
    -> horizontal accumulation triggers onHorizontalSwipe(+1/-1)
    -> ModuleShellView.switchModules selects next/previous
    -> ModuleRegistry.transitionDirection is set
    -> NotchRootView onChange(activeModuleID) recomputes open metrics

  Watchdog
    -> every 0.25 s: if mouse outside interactive rect, watchdogTick(true)
    -> after 0.5 s outside: closeImmediately(.watchdog)

14.3 Settings propagation

  SettingsStore is the single source of persisted user intent. It is an
  ObservableObject with @Published properties, and every setter writes to
  UserDefaults.

  NotchRootView.onAppear copies four values into NotchState:
    openOnHover (compile error), hoverIntentDelay, closeDelay, minStateDwell.

  NotchRootView.onChange then keeps these in sync:
    settings.openOnHover -> notchState.openOnHover (compile error)
    settings.hoverIntentDelay -> notchState.intentDelay
    settings.closeDelay -> notchState.closeDelay
    settings.minStateDwell -> notchState.minStateDwell

  Geometry settings are not copied; they are read on demand through
  NotchGeometry.live(for:settings:):
    fineTuneWidth, fineTuneHeight, topFlareRadius, bottomRadius,
    content assumptions, hotPaddingX (via InteractionRegion? check).

  Other settings are read directly by their consumers:
    hapticsEnabled, hapticPattern -> HapticsService
    mediaCompactEnabled -> MediaModule
    slowMotion, content assumptions -> Animations / ScaleBlur
    flyByGuardEnabled, flyBySpeedThreshold -> MouseMonitor
    verticalGesturesEnabled -> GestureMonitor

  Dead or partially wired:
    displayMode: written and read only inside SettingsStore. No consumer.
    handlerEnabled/handlerWidth/handlerHeight: NotchRootView has onChange
      handlers that call updateGeometry(), but updateGeometry() only
      recomputes closed metrics from NotchGeometry, which does not read these
      keys. They have no visual effect.
    openOnHover: persisted, exposed, copied to a non-existent property, and
      never consulted by enterIntent.
    contentInDelay, contentStagger, scrubPause, scrubProgress,
      openHapticPattern, closeHapticPattern: persisted and published but no
      consumer reads them. HapticsService uses hapticPattern only.

14.4 Media data pipeline

  Provider emits NowPlayingSnapshot
    -> NowPlayingService.accept(snapshot, from provider)
       - ignores updates from non-current providers
       - reconciles pending seek:
           if pending and track identity matches and target reached within
           tolerance, clear pending
           if pending and snapshot still shows old position, return without
           publishing (wait for the seek to land)
           if pending and track changed, clear pending and publish
       - updates snapshot, liveActivityState, providerName
    -> MediaView observes nowPlayingService
    -> MediaViewState(snapshot:) -> .empty or .track(MediaPresentation)
    -> MediaContentView renders
    -> MediaModule.isLiveActivityActive reads isPlaying and
       mediaCompactEnabled
    -> ModuleRegistry.activeLiveActivity returns the highest-priority active
       module
    -> NotchRootView.onChange(activeLiveActivity?.id) recomputes closed
       metrics (wings appear/disappear)

  Elapsed time:
    The service runs a 1 s Timer that calls refreshElapsed (or equivalent) to
    keep the published elapsed time moving even when the provider only sends
    metadata updates. MediaProgressBar additionally uses
    MediaPlaybackAnchor/TimelineView for smooth per-frame projection.

  Seek flow:
    1. User drags the progress bar.
    2. On release, MediaProgressBar calls onSeek(target).
    3. MediaTransport/MediaView calls NowPlayingService.seek(to:).
    4. Service records pendingSeek(target, issuedAt, trackIdentity) and sends
       the seek command to the provider.
    5. Subsequent snapshots are reconciled as above.
    6. If the target is not reached within seekTimeout (2 s), the pending seek
       should be cleared. In the current code the timeout check happens only
       when a snapshot arrives, so a silent provider can leave the pending
       state stuck. [INFERRED]

14.5 Module selection flow

  ModuleRegistry holds modules in order [Media, ModuleA, ModuleB].
  activeModuleID is optional. activeModule returns the selected module if it
  is enabled, otherwise the first enabled module, otherwise nil.
  selectNext/selectPrevious wrap around the enabled list and set
  transitionDirection to +1/-1.
  ModuleShellView.switchModules calls selectNext/selectPrevious on horizontal
  swipe.
  NotchRootView.onChange(activeModuleID) recomputes open metrics when the
  notch is open.

14.6 Screen selection flow

  ScreenResolver.preference defaults to .builtIn.
  targetScreen():
    - if preference == .followMouse, choose the screen containing the mouse,
      else fall back.
    - if preference == .builtIn, choose the built-in display, detected by
      CGDisplayIsBuiltin or safeAreaInsets.top > 0.
    - fall back to NSScreen.main.
  NotchPanel, NotchAttachment, NotchGeometry, InteractionRegion, Watchdog,
  and NotchRootView all call targetScreen() independently. There is no cached
  screen object, so a screen change is picked up on the next call, and the
  panel is repositioned by notifications.

14.7 Persistence flow

  SettingsStore setter -> UserDefaults.standard.set
  SettingsStore init -> UserDefaults.standard.object/string with defaults
  No migration or versioning. Keys are plain strings. Removing a key leaves
  stale data in UserDefaults. Adding a key uses the coded default until the
  user changes it.

  Panel frame is not persisted; it is recomputed from the target screen.
  Module selection is not persisted; it resets to the registry default on
  launch.

15.2 Canvas versus shape

  The panel is a fixed canvas of 568 x 220. The notch shape inside it is
  phase-dependent:
    closed: width = closed shape width (notch width or virtual 200) plus
            overlap, optionally widened by the live activity wings; height =
            notch height plus overlap.
    peek:   closed plus 8 x 3 (unreachable).
    open:   exactly the active module's preferredSize (420x180 for media,
            440x140 for Module A, 520x160 for Module B), pixel-aligned, with
            radii clamped to half the smaller dimension.
  The shape is top-aligned inside the canvas. The canvas is larger than the
  shape so the panel can host animation and hit margins without resizing the
  window.

15.3 Layer order and hit testing

  Layer order, back to front:
    1. Transparent canvas.
    2. Black NotchShape (the visible notch).
    3. ModuleShellView content, masked to the same shape.
    4. Compact view (closed only).
    5. Live activity (closed only).
    6. Context menu (attached to the ZStack).
    7. Calibration overlay (DEBUG).

  Hit testing:
    - The panel starts with ignoresMouseEvents = true.
    - NotchRootView.updateMouseInteraction sets ignoresMouseEvents based on
      whether the pointer is inside InteractionRegion.interactiveRect.
    - The black shape has an onTapGesture that toggles the notch.
    - ModuleShellView's tab buttons have .allowsHitTesting(true).
    - Compact and live-activity views have .allowsHitTesting(false).
    - The context menu is available when the panel accepts events.

  Because ignoresMouseEvents is toggled on every mouse move, clicks outside
  the interactive rect pass through to whatever is behind the panel. This is
  how the app avoids stealing clicks from the menu bar or desktop.

15.4 Closed state layout

  - Shape: notch-sized black pill with top flare and bottom radius.
  - If an active module has a compactView, it is shown only when the notch is
    closed and only if its centre 12xnotchHeight probe does not intersect the
    forbidden zone. The probe is centred at metrics.w/2 - 6, so it is a
    heuristic guard against placing content under the physical notch.
  - If an active module is a live activity (media playing and compact enabled),
    its liveActivity view is shown with opacity 0.9 and a 0.12 s ease-in-out
    animation on width. The shape widens to accommodate wings.
  - No content is scrollable or focusable while closed.

15.6 Tab bar geometry (verified problem)

  ModuleShellView computes:
    leftCount = ceil(enabledModules.count / 2)
    leftModules = first leftCount
    rightModules = the rest
    spacing = 4 (reduced to 3 once if a group does not fit)
    hitSize = 24
    iconSize = 14
    shapeWidth = active module preferred width (or 480 fallback)
    flanks = geometry.topBandFlanks(inShapeSpace: shapeWidth)

  In NotchGeometry.topBandFlanks(inShapeSpace:):
    leftWidth  = max(0, forbidden.minX - notch.minX)
    rightWidth = max(0, notch.maxX - forbidden.maxX)

  Because forbiddenZone is notchRect expanded by 6 on each side:
    forbidden.minX = notch.minX - 6  =>  leftWidth  = max(0, -6) = 0
    forbidden.maxX = notch.maxX + 6  =>  rightWidth = max(0, -6) = 0

  So both flanks are zero-width. [VERIFIED by arithmetic on verified code]

  The tab groups are then positioned with:
    left  x = flanks.left.maxX  - (groupWidth + 8)/2 + groupWidth/2
            = flanks.left.maxX - 4
    right x = flanks.right.minX + (groupWidth + 8)/2 - groupWidth/2
            = flanks.right.minX + 4

  A group of n tabs has content width A = n*24 + (n-1)*spacing and a leading
  or trailing padding of 8, so its total width is A + 8. Its centre is 4 points
  outside the zero-width flank, and it extends A/2 + 4 points on each side.
  For two tabs (A = 52), the group extends 30 points each way; the tab nearest
  the notch is centred about 14 points inside the notch. For one tab (A = 24),
  the tab is centred on the notch edge, so half of it overlaps the notch.
  [VERIFIED by arithmetic]

  The `.mask(NotchShape)` on ModuleShellView does not hide tabs that sit over
  the black notch; they are drawn on top of the black shape and can be visible
  or partially clipped depending on the exact shape path. Either way, the
  intended "tabs on the flanks" design is not achieved: the flanks are empty
  by construction.

  The test that is supposed to catch this,
  CompactLayoutTests.testTabPlacementForOneToSixModulesNoOverlap, asserts:
    XCTAssertGreaterThanOrEqual(flanks.left.width,
                                min(leftGroupWidth, flanks.left.width))
  which is tautologically true for any value. It provides no protection.
  [VERIFIED]

15.7 Interaction flows in detail

  Hover open:
    1. Global mouseMoved event enters the hot zone.
    2. MouseMonitor fires onEnterHotZone once per entry.
    3. NotchState.enterIntent runs; with default intentDelay 0 it calls
       requestOpen(.hover) immediately.
    4. Phase becomes .opening then .open.
    5. NotchRootView.onChange(.open) animates metrics to activeOpenMetrics
       with hoverOpen spring, then after 0.05 s fades/scales content in with
       contentIn.
    6. HapticsService plays .open (unless disabled or rate-limited).
    7. updateMouseInteraction expands the interactive rect to the open shape.

  Hover close:
    1. Global mouseMoved event leaves the open area.
    2. MouseMonitor fires onLeaveOpenArea.
    3. NotchState.cancelIntent, then requestClose(.mouseLeft).
    4. Phase becomes .closing; a close is scheduled after closeDelay (0 by
       default, so next main-queue turn).
    5. NotchRootView.onChange(.closed) hides content with easeIn 0.12 and
       animates metrics back to closedMetrics with closeFootprint.
    6. After 0.2 s, panel.ignoresMouseEvents = true.
    7. HapticsService plays .close.

  Click:
    The black shape has .onTapGesture { notchState.toggle() }. A click inside
    the interactive rect toggles open/close. The panel is nonactivating and
    does not become key, so the click does not bring the app forward.

  Watchdog:
    Every 0.25 s, if the pointer is outside the interactive rect and the phase
    is not closed, watchdogTick records outsideSince and closes after 0.5 s.
    This is a safety net for missed mouse-leave events (for example, when the
    pointer jumps or the app is busy).

  Module switch:
    A horizontal scroll gesture inside the interactive or hot rect is
    accumulated by GestureMonitor. When the threshold is crossed,
    onHorizontalSwipe(+1/-1) is called. ModuleShellView calls
    registry.selectNext/selectPrevious inside a contentOut animation. The
    registry updates activeModuleID and transitionDirection; the view's
    onChange recomputes open metrics if the notch is open.

  Settings:
    Right-click (context menu) -> Settings... -> SettingsWindow.shared.show().
    The settings window is a normal window, separate from the panel.

  Quit:
    Context menu -> Quit BilouNook -> NSApplication.shared.terminate(nil).

15.8 Accessibility and focus

  - The panel cannot become key or main, so standard keyboard focus is not
    available inside it.
  - Tab buttons are SwiftUI Buttons with .help tooltips and content shapes,
    but without an explicit accessibility label beyond the SF Symbol name.
  - The media transport controls are buttons with SF Symbols; VoiceOver labels
    depend on the symbol names and any labels set in MediaContentView.
  - There is no keyboard navigation for modules or transport controls.
  - Reduce Motion is honoured in some media animations (MediaMotion,
    MarqueeText) and in Animations.scaled? Animations.scaled only applies
    slowMotion, not reduceMotion. The root view's hardcoded animations do not
    consult reduceMotion. [VERIFIED for code paths; accessibility impact is

15.9 Visual risks

  - The black shape and the panel are separate; if the shape is smaller than
    the canvas, the area around it is transparent, which is intended.
  - The panel has no shadow; the shape relies on contrast with the desktop.
  - On displays without a notch, a virtual 200x32 notch is drawn at the top
    centre, which may look like a floating black pill.
  - On external displays, the app still draws the virtual notch unless the
    target screen is the built-in display. ScreenResolver defaults to the
    built-in display, so an external-only setup falls back to NSScreen.main.
  - Live activity wings can make the closed shape wider than the physical
    notch; the wing width is 36 points and the minimum content width is 120.

16.1 Animation vocabulary (Animations.swift)

  Name              Definition                                  Use
  ----------------- ------------------------------------------- -----------------
  hoverOpen         spring(response 0.28, damping 0.9)          open metrics
  openFootprint     spring(response 0.28, damping 0.9)          live activity widen
  hoverClose        spring(response 0.28, damping 1.0)          close metrics
  hoverClosePure    spring(response 0.28, damping 1.0)          close variant
  closeFootprint    spring(response 0.28, damping 1.0)          live activity narrow
  contentIn         spring(response 0.24, damping 0.9).delay(0.05) content appear
  contentOut        spring(response 0.18, damping 0.95)         content disappear
  scrubFollow       interactiveSpring(0.15, 1.0, blend 0.25)    progress follow
  scrubDrag         interactiveSpring(0.22, 0.58, blend 0.25)    progress drag

  timeScale = 1.0. scaled(_:) multiplies the animation by timeScale, with a
  minimum scale of 4.0 when SettingsStore.slowMotion is true.

  [VERIFIED]

16.2 Root view animations (hardcoded)

  - Content show/hide: spring(response 0.32, damping 0.9), applied with
    .animation(..., value: showContent) on ModuleShellView.
  - Closed content hide: Animation.easeIn(duration: 0.12).
  - Live activity width change: Animation.easeInOut(duration: 0.12).
  - Content appear after open: DispatchQueue.main.asyncAfter 0.05 s, then
    withAnimation(contentIn) { showContent = true }.
  - Closed after close: metrics animate with closeFootprint; content hides
    with easeIn 0.12; panel ignores mouse after 0.2 s.

  These hardcoded values bypass Animations.swift, so changing the central
  vocabulary does not change the root view's content spring or close easing.

16.3 Scale and blur transition

  ScaleBlur (ScaleBlur.swift) is a ViewModifier that reads
  contentScale_ASSUMPTION, contentBlur_ASSUMPTION, and
  contentAnchorY_ASSUMPTION from SettingsStore at init. Its body applies
  scaleEffect, blur, and opacity. AnyTransition.scaleBlur() composes it
  asymmetrically with contentIn/contentOut.

  Neither ScaleBlur nor scaleBlur() is referenced by any view. The separate
  ScaleBlurOpacityContentModifier in Animations.swift hardcodes 0.8 / 10 /
  -0.25 and is also unreferenced. The onAppear block in that modifier calls
  withAnimation with an empty closure and has no effect. AnimationLab's
  content-transition sliders bind to local @State, not SettingsStore, so they
  do not affect the running app. [VERIFIED by grep]

16.4 Media motion

  MediaMotion defines media-specific springs and checks reduceMotion for
  artwork and content transitions. MediaProgressBar uses a TimelineView at
  about 30 fps and an anchor projection rather than animating a stored value.
  EqualizerView uses a TimelineView at about 20 fps. MarqueeText disables
  scrolling when reduceMotion is on.

16.5 Haptic timing

  HapticsService cooldowns:
    same kind: 250 ms
    opposite kind: 120 ms
  The haptic is performed asynchronously on the main queue via
  NSHapticFeedbackManager.defaultPerformer.
  The service logs SKIP/PLAY lines with timestamps and reasons.

16.6 Measured motion (from checked-in docs)

  docs/motion-bench-before.md: close 1100 ms.
  docs/motion-bench-after.md: open 837.7 ms.
  docs/open-latency-before.md: intent 0.09 s, dwell 0.08 s, content delay
  0.16 s.
  docs/open-latency-after.md: effectively empty.

  These measurements were taken with older code. The current defaults are
  intent 0, dwell 0, content delay 0.05, close delay 0, and the springs above,
  so the numbers do not describe the current build. [VERIFIED drift]

16.7 Motion defects and risks

  - The open path has no deliberate minimum visible duration; with defaults,
    a fast pointer crossing can open and close within a few frames. The
    fly-by guard is off by default.
  - peekMetrics and the peek branch are dead, so there is no intermediate
    hover feedback even though the design documents describe one.
  - The content spring is duplicated (Animations.contentIn versus root 0.32)
    and can diverge.
  - The close animation starts immediately on mouse leave; there is no grace
    period unless closeDelay is raised in settings.
  - Animations.scaled honours slowMotion but not reduceMotion. Users who
    request reduced motion still get the notch open/close springs.
  - The live activity width animation uses easeInOut 0.12 rather than the
    central openFootprint/closeFootprint springs, so its feel differs from
    the notch open/close.

20. SECURITY AND PRIVACY
================================================================================

20.1 Threat model

  This is a local, single-user macOS utility. It is not a network service and
  does not process untrusted remote input. The relevant risks are:
    - Excessive OS permissions (Automation, Input Monitoring, Accessibility).
    - Private framework use and process execution.
    - Logging of user activity (mouse position, media metadata).
    - Unsigned or ad-hoc-signed binaries.
    - Supply-chain risk from vendored third-party code.
    - Crash or denial of service from malformed media metadata.

20.2 Apple Events and Automation

  The app sends Apple Events to Spotify and Music via NSAppleScript. Info.plist
  declares NSAppleEventsUsageDescription and NSAppleMusicUsageDescription, so
  macOS can show a purpose string. The user must still grant Automation
  permission per target app.

  The project enables hardened runtime and sets CODE_SIGN_ENTITLEMENTS to an
  empty string. Under hardened runtime, Apple Events generally require the
  com.apple.security.automation.apple-events entitlement. Without it, the
  AppleScript fallback may fail even after the user grants permission.
  [INFERRED; not reproduced]

  Recommendation: either add the automation entitlement or document that the
  AppleScript fallback requires a non-hardened build, and verify the actual
  TCC behaviour on the target macOS version.

20.3 Input monitoring

  Global monitors for mouseMoved and scrollWheel observe events delivered to
  other apps. On current macOS, some global event monitoring requires Input
  Monitoring permission, and synthetic event taps require Accessibility.
  The app does not declare NSInputMonitoringUsageDescription and has no
  onboarding for these permissions. If macOS blocks the monitors, hover and
  gesture interaction silently stops working. [INFERRED]

  Recommendation: test on a clean user account, add the appropriate usage
  description if required, and provide a fallback (polling watchdog already
  exists for mouse position, but it depends on NSEvent.mouseLocation, which
  does not require a monitor).

20.4 Private framework and process execution

  MediaRemoteNowPlayingProvider executes /usr/bin/perl with a bundled script
  and framework path resolved from Bundle.main.resourceURL. The path is not
  user-controlled, and arguments are fixed command tokens plus a numeric seek
  value. There is no shell invocation and no string concatenation into a shell
  command. This is reasonably safe against injection.

  Risks:
    - The private MediaRemote framework is unsupported and may change.
    - The bundled framework is ad-hoc signed, not notarized.
    - A compromised app bundle could execute arbitrary Perl, but that is
      equivalent to any code in the app.
    - The Perl script and framework are third-party code with their own
      security posture; they were not audited line-by-line here.

20.5 Logging and privacy

  - MouseLog writes mouse coordinates to /tmp/bilounook_mouse.log in DEBUG.
    /tmp is world-readable by default on macOS, so other local users could
    read pointer coordinates. This is DEBUG-only and low sensitivity.
  - MediaSeekDebugLog writes seek activity to ~/Library/Logs/BilouNook/seek.log
    in DEBUG. User-only by default.
  - Haptics and hotkey logs use OSLog; they contain no media metadata.
  - NotchAttachDiagnostics prints screen geometry and menu-bar owner names to
    stdout in DEBUG; no personal data beyond window owner names.
  - The app does not log track titles or artwork to persistent logs in release
    builds.

20.6 Network

  The app itself makes no network requests. The vendored adapter is local.
  There is no analytics, telemetry, crash reporting, or update checker.
  [VERIFIED by source search for URLSession/Network; the Perl adapter could in
  principle do more, but its documented purpose is local MediaRemote access]

20.7 Secrets

  No API keys, tokens, passwords, certificates, or provisioning profiles are
  present in the tracked tree. The only signing configuration is an empty
  entitlements setting and ad-hoc signing in the runtime script. [VERIFIED]

20.8 Sandbox and entitlements

  No App Sandbox entitlement. The app can read files, launch processes, and
  send Apple Events subject to TCC. Hardened runtime is enabled but no
  hardened-runtime exceptions are declared.

20.9 Supply chain

  The vendored MediaRemoteAdapter is BSD-3-Clause. Its LICENSE file is
  present. The recovered tree flattens the original gitlink/submodule into
  Vendor/, so the exact upstream commit is not pinned in the recovered
  repository. The original snapshot recorded gitlink 0e82bf1c, but the
  corresponding submodule content is not verifiable from the recovered tree.
  This weakens reproducibility and provenance. [VERIFIED structural gap]

20.10 Robustness against malformed media data

  - JSON decoding is guarded and failures are reported to the service.
  - Snapshots with empty or untitled payloads are rejected by tests.
  - Artwork decoding uses ImageIO and returns nil on invalid data.
  - AppleScript parsing splits on "|" without escaping, so metadata
    containing "|" corrupts fields. This is a correctness bug, not a security
    vulnerability.
  - Very large artwork could consume memory during base64 decode and
    thumbnail generation; the thumbnail cache is bounded by pixel size, not by
    total bytes. [INFERRED]

20.11 Security recommendations

  1. Decide whether the app is distributed; if so, replace ad-hoc signing with
     Developer ID signing and notarization, and add the automation entitlement
     if Apple Events are required.
  2. Add Input Monitoring onboarding or verify that the monitors work without
     it on the supported OS versions.
  3. Move DEBUG logs out of /tmp or set restrictive permissions.
  4. Pin the vendored adapter to an upstream commit and record it in a
     lockfile or submodule.
  5. Add a size limit for artwork payloads before base64 decode.
  6. Escape or length-prefix fields in the AppleScript transport instead of
     using "|" delimiting.

  H-1  Peek phase is unreachable

       NotchGeometry has peekMetrics(), both dead. STATE_MACHINE.md and

       Direction: either implement a real peek transition with timing, or

       SettingsStore persists openOnHover (default true). NotchRootView copies

       intentDelay. There is no branch that checks the setting. [VERIFIED]
       Impact: turning hover-to-open off does nothing; behaviour cannot be

  H-3  Duplicate time row and height budget mismatch
       MediaProgressBar renders a track and a time row. MediaContentView then
       renders its own time row after the progress bar. MediaLayout.contentHeight

       Impact: two time rows appear; the content exceeds its planned height;
       spacing and control positions can overflow or compress.
       Direction: choose one owner for the time row. If MediaProgressBar owns
       it, remove the second row and its spacers. If MediaContentView owns it,
       remove it from MediaProgressBar and update contentHeight accordingly.

  H-4  Tab bar flanks are zero-width
       NotchGeometry.topBandFlanks computes leftWidth = forbidden.minX -
       notch.minX and rightWidth = notch.maxX - forbidden.maxX. Because the
       forbidden zone is the notch expanded by 6, both values are -6 and are
       clamped to 0. [VERIFIED]
       Impact: the "tabs on the flanks" layout places groups over the notch.
       For a two-tab group, the nearest tab is centred about 14 points inside
       the notch; a one-tab group is centred on the notch edge, so half of it
       overlaps the notch. The mask does not move the tabs out of the notch.
       Direction: define flanks as the region between the notch edge and the
       shape edge (or between the forbidden zone and the shape edge), not
       between the notch and the forbidden zone. Recompute placement from the
       new rects. Replace the tautological tests with exact frame assertions.

       compiled. [VERIFIED]

       and the app icon setting for now.

  H-6  No lifecycle teardown in NotchRootView
       onAppear starts MouseMonitor, Watchdog, GestureMonitor, and registers a
       workspace sleep observer. There is no onDisappear to stop them or
       remove the observer. [VERIFIED absence]

       is limited, but it blocks previews, tests, and future multi-window use.

22.1 Prerequisites

  macOS 14.6 or later.
  Xcode with the macOS SDK (the project was authored with Xcode 14+ format and
  LastUpgradeVersion 1500).

  /usr/bin/perl must exist for the MediaRemote provider.
  The MediaRemoteAdapter.framework must be built before running the app with
  the MediaRemote provider.

22.2 Building the adapter and runtime

  Step 1: build the universal framework

    ./scripts/build-mediaremote-adapter.sh

  This uses xcrun --sdk macosx clang -dynamiclib -arch arm64 -arch x86_64
  -mmacosx-version-min=14.6 -fobjc-arc over Vendor/MediaRemoteAdapter/src,
  writes a framework Info.plist with CFBundleIdentifier
  com.bilou.MediaRemoteAdapter, and creates the expected symlinks.

  Step 2: prepare the runtime

    ./scripts/prepare-nowplaying-runtime.sh <destination>

  This copies bin/mediaremote-adapter.pl and the built framework into
  <destination>/NowPlaying/ and ad-hoc codesigns the framework.

  In the Xcode build, the "Prepare Now Playing Runtime" shell phase runs the
  preparation automatically with the built products directory as destination.
  The phase is alwaysOutOfDate, so it runs on every build.

    - no installer or DMG script,

    1. Restore Assets.xcassets and the AppIcon set.

26. FINAL UNDERSTANDING AND HANDOVER NOTES
================================================================================

26.1 What this project is, in plain language

BilouNook is a personal macOS notch utility. It turns the black notch area at
the top of a MacBook screen into an interactive surface. Hovering or clicking
opens a black rounded panel that can show a media player, and while music is
playing a compact strip can extend the notch to show artwork and an equalizer.
The app is deliberately invisible in the Dock and does not take focus. It is a
single-user, local tool, not a commercial product.

The code shows a developer who cares about feel: spring constants are tuned,
there is an animation lab and a motion benchmark, haptics are rate-limited,
the notch geometry is pixel-aligned, and there is a substantial test suite for
geometry and media math. The project also shows the cost of rapid iteration:
the documentation and the code have drifted apart, the Xcode project has
accumulated a UUID collision and a missing asset catalog, and the final state
does not compile.

26.2 Current state

  Build:        FAILS at ModuleShellView.swift:77:16 (type-check timeout).
  Second error: NotchRootView.swift:150 and :226 reference a missing
                NotchState.openOnHover.
  Tests:        Not run; the test target compiles the same failing sources.
  Project:      UUID collision C3000001, missing Assets.xcassets, MotionBench
                absent from the Debug group, non-standard Info.plist UUID.
  Runtime:      Not observed. Static analysis only.
  Docs:         Partly stale; current code is authoritative.
  Recovery:     149/149 tracked files materialised and hash-verified; a few
                files are best-effort reconstructions, listed in section 25.

26.3 What a new maintainer should do first

  In order:
    1. Read sections 14 (state), 15 (UI), and 21 (bugs).
    2. Fix C-2 (openOnHover) and C-1 (ModuleShellView) to get a build.
    3. Fix the Xcode project and restore or remove Assets.xcassets.
    4. Run xcodebuild build and test. Do not trust any document until the
       build is green.
    5. Fix the tab flank geometry and the duplicate media time row.
    6. Decide the hover model (direct open vs peek) and make code, tests, and
       docs agree.
    7. Add lifecycle teardown and remove dead settings.
    8. Only then tune motion and polish.

26.4 What is safe to change and what is fragile

  Safe to change:
    - Documentation, once it is marked historical or updated.
    - Placeholder Module A and Module B.
    - Settings UI (currently minimal).
    - Debug tools, as long as they stay behind #if DEBUG.
    - Animation constants, provided all call sites use Animations.scaled.

  Fragile:
    - NotchGeometry and NotchShape: many tests and the panel attachment depend
      on exact pixel alignment and radii.
    - NotchState: timing and generation logic is subtle; preserve the fake
      clock/scheduler tests.
    - NowPlayingService: pending-seek reconciliation is the most complex logic
      in the project; the 20-test suite is the safety net.
    - MediaLayout: the height budget is duplicated in views; change the view
      and the constants together.
    - The Xcode project: hand-editing UUIDs is error-prone; validate every
      reference after a change.
    - The MediaRemote adapter integration: private framework and Perl process;
      changes can break silently on OS updates.

26.5 Handover checklist

  [ ] Confirm the recovered tree is the intended baseline; tag it.
  [ ] Fix the two compile errors.
  [ ] Repair the Xcode project and asset catalog reference.
  [ ] Build and run the app on a notched MacBook.
  [ ] Verify panel level, click-through, hover open/close, and watchdog.
  [ ] Verify media playback with Apple Music, Spotify, and a browser.
  [ ] Verify seek, previous/next, and live activity.
  [ ] Verify haptics on a Force Touch trackpad.
  [ ] Verify Settings persistence across launches.
  [ ] Run the test suite and record the result.
  [ ] Update or archive stale docs.
  [ ] Decide distribution scope and signing.
  [ ] Back up the project outside the Desktop.

26.6 Final assessment

  The project is a promising, well-intentioned personal utility with a solid
  geometric and state-machine core. Its current recovered state is not
  runnable, but the failures are concrete and fixable: two Swift compile
  errors, a project-file integrity problem, a missing asset catalog, and a
  handful of layout/state mismatches. None of these require a rewrite. The
  architecture can support the intended feature set; the main risks are
  documentation drift, lifecycle ownership in the root view, and the
  fragility of the private MediaRemote integration.

  The most important next step is not more analysis. It is to make the project
  build, then run it on the target hardware and compare the observed behaviour
  with the intended behaviour described in sections 14-16.

GLOSSARY
================================================================================

Anchor (MediaPlaybackAnchor)
  A value that stores elapsed time at a known date and projects it forward,
  so progress can be rendered smoothly without mutating state every frame.

Apple Event / Automation
  macOS inter-application messaging. Sending events to Music or Spotify
  requires user consent and, under hardened runtime, usually an entitlement.

Blob
  A Git object containing file content, identified by a SHA-1. The snapshot
  store used blobs to preserve file contents.

Build phase
  An Xcode step in a target: Sources, Resources, Frameworks, or a custom shell
  script.

Canvas
  The fixed 568x220 NSPanel area in which the phase-dependent notch shape is
  drawn.

Carbon hotkey
  A legacy macOS API for global keyboard shortcuts, used only in DEBUG builds.

Closed metrics
  The notch footprint when the notch is collapsed: notch width/height plus
  overlap, optionally widened by live-activity wings.

Dwell time
  A minimum time a state must remain before another transition is allowed
  (minStateDwell in NotchState).

Flank
  The area beside the physical notch in the top band, intended for module
  tabs. In the current code the computed flanks are zero-width.

Forbidden zone
  The notch rectangle expanded by 6 points on each side, used to keep content
  out from under the physical notch.

Generation counter
  A monotonically increasing number in NotchState used to invalidate stale
  scheduled closures.

Gitlink
  A Git tree entry that points to a submodule commit rather than a file. The
  original third_party/mediaremote-adapter was a gitlink.

Hardened runtime
  A macOS code-signing hardening option that restricts dangerous operations,
  including some Apple Events, unless specific entitlements are present.

Hot zone
  The closed-notch hit area expanded by horizontal padding and a 6-point top
  extension, used to detect hover intent.

Interactive rect
  The rectangle in which the panel accepts mouse events for the current phase.

Live activity
  A compact module view shown while the notch is closed (for example, artwork
  and an equalizer while media plays).

Live activity wings
  Horizontal extensions added to the closed notch to make room for live
  activity content. Wing width is 36 points.

Module
  A pluggable unit implementing NotchModule, with compact and expanded views,
  a preferred size, and optional live activity.

Notch
  The physical black camera housing area at the top of a MacBook display, or a
  virtual 200x32 substitute on displays without one.

NotchState
  The @Observable phase machine that owns open/close intent, delays, dwell,
  and watchdog behaviour.

Open metrics
  The expanded notch footprint, equal to the active module's preferred size,
  pixel-aligned with clamped radii.

Panel
  The borderless, non-activating NSPanel that hosts the notch UI above the
  menu bar.

Peek
  A declared intermediate phase between closed and open. It is currently
  unreachable.

Pending seek
  A seek command that has been sent but not yet confirmed by a provider
  snapshot. It carries target time, issue date, and track identity.

Provider
  A NowPlayingProvider implementation that supplies snapshots and accepts
  commands (MediaRemote or AppleScript).

Snapshot (NowPlayingSnapshot)
  A value describing the current track, playback state, elapsed time,
  duration, artwork, and source app.

Snapshot store
  The read-only OpenCode blob/tree store used to recover file contents.

TCC
  Transparency, Consent, and Control: the macOS privacy permission system for
  Automation, Input Monitoring, Accessibility, and similar capabilities.

Tree hash
  A SHA-1 over a Git tree object's sorted entries; used to verify directory
  contents during recovery.

Wings
  See live activity wings.

XCTest
  Apple's unit-test framework, used by all 18 test files.

Evidence labels
  VERIFIED: directly read or reproduced.
  INFERRED: conclusion from verified evidence, not directly proven.
  UNVERIFIED: could not be checked because evidence was lost or unreadable.
